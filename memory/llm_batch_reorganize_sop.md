# LLM Batch Reorganize SOP

## Struct Header
- Reader: GA 总控
- When to read: 需要用 AI 对大批数据进行语义分类/整理/重组时
- Trigger: 收藏夹整理、邮件分诊、文件归类、书签整理、客户分级、简历筛选等
- Inputs: 数据列表（API拉取或本地文件）、分类目标描述
- Outputs: 分类计划 JSON + 执行结果报告
- Tools: authenticated_fetch_skill(K1), llm_json_distill_skill(K2), web_execute_js
- Side effects: 数据移动/重命名/标签修改（写入操作）
- Risk: R2(可撤销的批量修改)
- Failure path: API拉取失败→检查登录态；分类不合理→调整 prompt；写入失败→检查参数格式；部分失败→跳过+报告
- Review: 执行写入前必须展示分类计划给用户确认

## 核心流程: 拉取 → 分类 → 确认 → 执行 → 验证

### Phase 1: 数据拉取
**确认点:** 拉取完成后用 `ask_user` 展示数据量和示例条目，确认继续。

1. 用 K1 拉取全量数据列表（处理分页）
2. 提取关键字段（标题、描述、标签、时间等）
3. 确定目标分类体系（用户指定或 AI 建议）

### Phase 2: LLM 语义分类
1. 用 K2 将全量条目一次性喷给 LLM
2. 输出: 每个条目的目标分类 + 置信度
3. 模糊条目归“其他”，禁止强制分类

### Phase 3: 人在回路确认
**gate:** 用户未明确确认前，禁止进入 Phase 4。
**进度报告:** 展示分类计划表格 + 统计信息（各类别数量、模糊条目数）。

1. 向用户展示分类计划（表格形式）
2. 用户可修改/拒绝/确认
3. **禁止未经确认直接执行**

### Phase 4: 批量执行
1. 按计划逐条执行写入操作
2. 每批 5-10 条，间隔 300ms
3. 失败条目记录并跳过，不阻塞其他

### Phase 5: 验证
**gate:** 验证失败率 >10% 时，用 `ask_user` 询问是否回滚。
**进度报告:** 向用户汇报最终结果：成功/失败/跳过数量。

1. 重新拉取数据确认变更生效
2. 报告: 成功/失败/跳过数量

## 关键约束

1. **语义优先**: 禁止关键词硬匹配，必须用 LLM 语义理解
2. **人在回路**: 执行前必须展示计划，用户确认后才执行
3. **幂等安全**: 同一条目重复执行不应产生副作用
4. **参数精确**: API 写入时用 URLSearchParams 构造，禁手工拼接
5. **模糊归“其他”**: 宁可不分，不可分错

## 常见坑

- B站收藏夹 API 参数名是 `resources` 而非 `res_media_ids` → 查文档确认
- 批量操作触发频率限制 → 加延迟 + 分批
- 分类体系与已有标签/文件夹不匹配 → 先查询已有结构再设计
- 数据量超过 LLM context → 分批蒸馏，最多 200 条/批
